# M1: inspectable memory across sessions

User goal: submit a decision, inspect what the system proposes to remember,
confirm or correct it, and resume the right topic after restarting.

The first milestone is a text-based vertical slice using finalized transcript
input. Audio capture and real-time voice playback are a later milestone.

## Acceptance flow

1. Submit a finalized transcript with stable workspace/branch/session identity.
   Retrying it creates one task; partial input never becomes durable memory.
2. See task state and candidates with source evidence and provider identity.
   Extraction itself does not silently confirm a candidate.
3. Select candidates to confirm, or correct a value with a new attributed event.
   History remains visible; corrections do not destroy the original record.
4. Switch topics/branches without leaking another branch's decisions.
5. Close and reopen the app/process, resume the selected branch, and retrieve the
   latest confirmed record with provenance. Pending tasks remain recoverable.
6. Show extraction failure, retry and unresolved conflict states clearly.

Existing command APIs cover parts of this flow. A usable memory inspection/edit
surface, correction semantics and natural-language extraction quality still need
implementation. This document defines acceptance, not completed product features.

## Shared contracts

- Providers produce candidate records; confirmation writes memory events.
- A routing result retains provider identity, evidence and attempt trace.
- Experiments substitute the router/provider without changing confirmation or
  branch/version semantics.
- The stable default path remains available when an experiment is enabled.

Before a multi-user deployment, define authentication, ownership and access
isolation separately. M1 is a local single-user reference product.
